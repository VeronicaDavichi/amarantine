# 记忆工具使用指南（Memory Tool Guide）

> **本文件是单一源头**：构建时从本文生成 MCP `initialize` 响应的 `instructions` 字段。
> 工具 schema 变更后必须同步本文件，并跑 `harness/check-guide.py` 校验（见 §7）。

---

## 0. 你有 4 个长期记忆工具

| 工具 | 一句话 |
|---|---|
| `memory_recall` | 查过去发生的事 |
| `memory_remember` | 记下值得长期保留的事 |
| `memory_forget` | 用户要求忘记时删除 |
| `memory_feedback` | 回报本次回答引用了哪些记忆 |

记忆是**跨会话持久**的。你现在看到的对话，可能是几天后用户再提起的素材。

---

## 1. `memory_recall` — 什么时候查

### 应该查

| 信号 | 例子 |
|---|---|
| 用户指代过去 | 「上次」「之前」「那个项目」「我们说好的」 |
| 用户问你记不记得 | 「你还记得吗」「我跟你说过」 |
| 你要陈述**具体事实** | 日期、决定、偏好、承诺、人名关系 |
| 用户说的事可能和以前冲突 | 「我现在改主意了」 |

### 不应该查

- 纯知识问答（「Python 怎么读文件」）
- 寒暄、闲聊
- 答案已在本轮上下文中

### 例子

```
用户：上次说换工作那事后来怎样了？
→ memory_recall({ "query": "换工作 进展 决定", "token_budget": 2000 })
```

> 召回结果里 `materials=[]` 表示**确实没有相关记忆**。此时应直接说「我没有相关记录」，**不要**编造。

## 2. `memory_remember` — 什么时候记

### 应该记

| 类型 | 例子 |
|---|---|
| 用户明确要求 | 「帮我记一下」「记住这个」 |
| 长期有效的决定 | 「我决定接受这个 offer」 |
| 约定与承诺 | 「下周三之前给你答复」 |
| 状态变化 | 「我换部门了」「我搬家了」 |
| 稳定偏好 | 「我不吃香菜」「我习惯用 Vim」 |
| 用户纠正你的错误认知 | 「不是这样，其实是……」 |

### 不应该记

- 临时信息（时间、天气、当场情绪）
- 闲聊与玩笑
- 从对话上下文能直接推出来的内容
- 用户的隐私信息（除非用户明确要求记住）

### `summary` 怎么写 —— **最容易出错的地方**

**格式：谁 + 做了什么 + 结果如何。必须具体。**

| ❌ 错误（抽象） | ✅ 正确（具体） |
|---|---|
| 主人换了工作 | 主人 2026 年 3 月决定接受 A 公司 offer，因为通勤从 1.5 小时降到 20 分钟 |
| 用户在考虑一件事 | 主人在考虑是否接受新 offer，顾虑团队氛围，暂未决定，等下周三对方补薪资方案 |
| 生气了 | 主人因项目上线延期与领导争执，决定下次提需求时先确认排期 |
| 讨论了技术方案 | 主人决定用 FastAPI 而非 Flask，因为要原生 async 做并行扇出 |

**为什么必须具体**：`summary` 是唯一被向量化的字段。写得抽象，就会和几十张其它卡在向量空间里糊成一团，召回时谁也分不出来。

### 参数怎么填

| 参数 | 什么时候填 |
|---|---|
| `pinned: true` | **只有**用户明确要求「记住」时。别自作主张 |
| `important: true` | 用户强调「这很重要」「千万别忘」时 |
| `emotion_intensity` | 用户情绪明显强烈时填 0–1；**它只加分，不构成保护** |
| `date_hint` | 有时间线索时填自然语言（「上个月」「去年底」），服务端会解析 |

⚠️ **不要**因为「你觉得这件事重要」就填 `pinned: true`。服务端只认参数，且会统计频率——滥用会被降级。

## 3. `memory_forget` — 什么时候忘

### 应该忘

- 用户说「忘了这个」「删掉那条」「不用记了」
- 用户明确指出某条信息已经过时，且不需要保留

### 不应该忘

- 你**自己觉得**某条不重要
- 用户只是表达情绪（「真是服了」不是删库指令）

> 删除是**软删**：检索不到，但原文仍保留供审计。这一点可以对用户说明。

---

## 4. `memory_feedback` — 怎么回报

- 本次回答里**实际引用**了哪些材料，就报哪些（填它们的 `event_id`）
- 一条都没用到 → **不要调用**
- 不许虚报：服务端会校验 `trace_id` 是否真的返回过这些 id

> 这个工具的意义：让系统知道哪些记忆真的有用。虚报会让保护机制失效。

---

## 5. 反模式清单

| 反模式 | 后果 |
|---|---|
| 一次性把整段对话 `remember` 下来 | 产生大量碎片卡，召回时互相干扰 |
| 每轮对话都 `recall` | 增加延迟，且污染 `recall_count` 统计 |
| `summary` 写成抽象概括 | 向量糊在一起，等于没记 |
| 用情绪强度换保护 | 「气死我了」不等于「值得记十年」，会被降级 |
| 虚报 `feedback` | 污染 `confirmed_by_use`，保护机制自我废止 |
| 召回为空时编造内容 | 直接违背溯源原则，比不回答更糟 |

## 6. 典型场景

### 场景 A：用户要求记住

```
用户：帮我记一下，下周三要去杭州出差，顺便问下小王那个项目的进度

→ memory_remember({
    "summary": "主人计划下周三去杭州出差，行程包含与小王确认项目进度",
    "date_hint": "下周三",
    "pinned": true
  })
```

### 场景 B：用户提起旧事

```
用户：之前那个offer的事，我后来拒了

→ memory_recall({ "query": "offer 决定" })      # 先查旧的
→ memory_remember({
    "summary": "主人最终拒绝了该 offer，未说明原因",
    "date_hint": "最近",
    "important": false
  })
```

### 场景 C：用户要遗忘

```
用户：把上次那条忘了吧

→ memory_recall({ "query": "上次那条" })        # 先定位
→ memory_forget({ "event_id": "evt_...", "reason": "user_forget" })
```

## 7. 维护约定

- 本文是 MCP `instructions` 的**唯一源头**，代码里不另写一份
- 工具 schema 变更后**必须**同步本文
- 一致性校验：

```bash
python harness/check-guide.py
```

校验内容：每个 tool 是否在本文出现、参数名是否与 inputSchema 一致、枚举值是否一致。不一致 → 非零退出。

- **定时校验**由你自己的 crontab 驱动（不内置调度器）：

```bash
# .env
GUIDE_CHECK_CRON=0 9 * * 1        # 每周一 9:00

# 安装（复制执行）
(crontab -l 2>/dev/null; echo "$GUIDE_CHECK_CRON cd /path/to/amarantine && python harness/check-guide.py >> logs/guide-check.log 2>&1") | crontab -
```
