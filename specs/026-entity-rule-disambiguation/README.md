# 026 C.B3 三级实体消歧（② 级改为确定性规则层）

## Overview

016 记录了「C.B3 要三级消歧，现在只有第三级」，并担心「0.92/0.85 是拍的初值，
中文实体名的余弦分布未必适用」。**这个担心被实测证实了，而且比预期严重。**

### 实测：向量在中文实体名上不可分（2026-11-06，bge-m3，14 组对照）

| 余弦 | 应合并 | 类型 | pair |
|---|---|---|---|
| 0.9435 | ✅ | 地名加后缀 | 北京 / 北京市 |
| 0.9257 | ✅ | 加后缀 | 腾讯 / 腾讯公司 |
| 0.8912 | ✅ | 全称/简称 | 阿里 / 阿里巴巴 |
| **0.8801** | ❌ | 加后缀但不同实体 | **项目A / 项目A组** |
| **0.8514** | ❌ | 只差一个字母 | **项目A / 项目B** |
| 0.7928 | ✅ | 加后缀 | 豆包 / 豆包助手 |
| **0.7763** | ✅ | 加后缀 | **豆包 / 豆包AI** |
| 0.7237 | ✅ | 加称呼 | 张三 / 张三哥 |
| 0.6683 | ❌ | 单字前缀(不同人) | 李四 / 李四光 |
| 0.6143 | ✅ | 跨语言 | 微信 / WeChat |
| 0.5925 | ❌ | 单字前缀(不同人) | 张三 / 张三丰 |
| 0.5817 | ❌ | 同后缀不同地名 | 北京 / 南京 |
| **0.4806** | ✅ | 同义表达 | **周会 / 每周例会** |
| 0.3487 | ❌ | 完全不同 | 张三 / 李四 |

**该合并的最低 0.4806，不该合并的最高 0.8801 —— 区间完全重叠，8 组应合并里 5 组落在重叠区。**

按 ADR 原阈值实测：

| 阈值 | 误并（不该合并却被合并） | 漏并（该合并却没合并） |
|---|---|---|
| 0.92（`ENTITY_ALIAS_SIM`） | 0/6 | **6/8，几乎全漏** |
| 0.85（灰区下限） | 2/6 | 5/8 |
| 0.75 | 2/6 | 3/8 |

**这不是「阈值需要标定」，是特征本身不可分。** 任何单一阈值都同时造成误并和漏并。

### 这是同一模式的第二次重演

016 里已经记录过编辑距离被实测否定（该合并的 0.50 < 该区分的 0.67）。
换成向量，排序**依然是反向的**。两次都说明同一件事：

> **中文实体名的字面/向量相似度，与「是否同一个实体」没有稳定相关性。**

### 决策（2026-11-06 用户拍板）

| 问题 | 决定 |
|---|---|
| ② 级怎么做 | 改成**确定性规则层**（不用向量） |
| 覆盖形态 | 字面包含+后缀白名单、单字名前缀冲突、称呼后缀剥离、同义表达 |
| 风险控制 | **默认开启，配置可关** |

`ENTITY_ALIAS_SIM` 不再有消费点 —— **保留但标为「实测不可用」**，
不删（ADR 里是正式配置项，删掉会丢失这段历史；将来换模型可重新评估）。

## Design

### D1 为什么是「规则层」而不是「更好的阈值」

因为要判定的东西**本质是语义知识**，不是数值距离：

- `豆包 / 豆包AI` 该合并、`项目A / 项目A组` 不该合并 —— 两者都是「加后缀」，
  向量给 0.7763 / 0.8801，**后者更高**。
- 区别不在字面，在于「豆包AI 是豆包的产品名」这个**世界知识**。

向量给不了世界知识。规则层也不给，但规则层能**确定性地**覆盖那些
「有明确字面规律」的情形，把剩下的交给 LLM —— 这比「所有情形都靠向量猜」
更可审计。

这也回到 ADR C.B3 的原话：

> 别名表是可复查的事实，模型推理不是。

规则层是「可复查的事实」的自动化版本：**每条判定都能说清依据**。

### D2 四级判定（按顺序，命中即返回）

新模块 `memory/services/entity_match.py`：

```
def match_entities(a, b, *, settings) -> MatchResult
```

`MatchResult` 有三态：`SAME` / `DIFFERENT` / `UNKNOWN`，带 `reason`（可入日志）。

| 顺序 | 规则 | 裁定 | 依据 |
|---|---|---|---|
| 1 | 单字名前缀冲突（复用 spec 020） | `DIFFERENT` | 张三/张三丰 |
| 2 | 称呼后缀剥离后相等 | `SAME` | 张三哥/张三、王总/王经理 |
| 3 | 字面包含 + 后缀在白名单 | `SAME` | 豆包/豆包AI、北京/北京市 |
| 4 | 同义词表命中 | `SAME` | 周会/每周例会 |
| 5 | 都不命中 | `UNKNOWN` | 交给 ③ LLM |

**顺序不能换**：1 必须在 3 之前。否则 `张三/张三丰`（「丰」若在白名单里）
会被 3 判成相同。这是 016 已实测过的坑。

### D3 称呼后缀剥离必须是「双向且对称」

`张三哥` → `张三`；`张三` 剥不出东西 → 保持。判定时**双向剥**：

```
strip(a) == strip(b) 且至少一边真的剥掉了东西  ->  SAME
```

「至少一边剥掉了」很重要：`张三` 和 `张三` 相等但不是剥离导致的，
不该算这条规则的功劳（虽然结果一样，但会污染审计日志的原因字段）。

称呼表：`总 / 经理 / 老师 / 哥 / 姐 / 先生 / 女士 / 同学 / 工`

**注意 `工`（李工）和 `总`（王总）在中文里极常见**，但也很容易误伤
（`总经理` 不是「总经理」加称呼）。所以剥离前要求**剥完长度 >= 2**，
且剥完不能是空串。

### D4 字面包含 + 后缀白名单：白名单是核心

不是「谁包含谁就合并」—— 那样 `项目A` / `项目A组` 会误并。

```
短的是长的前缀 且 多出来的部分 ∈ 后缀白名单  ->  SAME
```

后缀白名单（可配置）：`AI / 助手 / 公司 / 集团 / 科技 / 股份 / 有限公司 /
市 / 省 / 县 / 区 / 镇 / 部 / 处 / 科 / 组（？）`

**`组` 要不要进白名单？** 实测 `项目A / 项目A组` = 0.8801 不该合并，
但 `研发组 / 研发` 可能该合并。**这是真实歧义，规则层判不了。**

决定：**`组` 不进白名单**（保守，宁可漏并不误并）。漏并的代价是
「同一实体多一个节点」，误并的代价是「两个实体混成一个」，后者更糟。

### D5 同义表达必须用词典，不能靠规则

用户要求覆盖「周会/每周例会」，但这一对：

- 字面不包含（`周会` 不是 `每周例会` 的前缀）
- 余弦 0.4806（低到几乎不相关）

**任何规则都判不出来。** 所以实现成**可配置的同义词表**：

```
ENTITY_SYNONYMS=周会=每周例会,例会=每周例会,豆包=豆包AI
```

命中即 `SAME`。未命中的同义表达降级给 LLM。

这是诚实的做法：**承认规则的能力边界**，而不是假装能判。

### D6 配置项

| 配置 | 默认 | 说明 |
|---|---|---|
| `ENTITY_RULE_ENABLED` | `true` | 总开关。关掉则完全回退到「只有 ③ LLM」的现状 |
| `ENTITY_SUFFIXES` | `AI,助手,公司,...` | 后缀白名单（逗号分隔，**替换**默认值） |
| `ENTITY_HONORIFICS` | `总,经理,老师,...` | 称呼表（同上） |
| `ENTITY_SYNONYMS` | `周会=每周例会` | 同义词表（`a=b,c=d`，双向生效） |

**空字符串的语义**：`ENTITY_SUFFIXES=` （显式空）表示「禁用这条规则」，
不是「用默认值」。这和 `TOKENIZER` 那类「有意不接」的惯例保持一致 ——
显式给空就是不要这个功能。

### D7 接线点：`resolve_one` 里 LLM 之前

```python
# 现状：单字前缀检查 → LLM
# 改后：规则层（含单字前缀）→ SAME 则直接返回 / DIFFERENT 则返回 None → 否则 LLM
```

规则判 `SAME` 时返回：

```python
AliasClaim(alias=..., canonical=..., label=ALIAS_PROBABLE, source="rule")
```

`probable` 不是 `exact`：规则推断的把握不如用户明说，该标出来。
`source="rule"` 已经存在于 `AliasClaim` 的 Literal 里 —— 当初就为规则留了位置。

**`ENTITY_RULE_ENABLED=false` 时必须完全等价于改动前**：单字前缀检查保留
（它本来就是 spec 020 的独立功能，不属于这次新增），其余规则跳过。

## Notes

### 为什么 `ENTITY_ALIAS_SIM` 保留不删

它现在是「实测不可用」，但：
- ADR 里是正式配置项，删掉会丢失这段测量历史
- 将来换 embedding 模型（如专门的实体嵌入）可以重新评估
- 它属于「有意保留但当前无效」，和 `TOKENIZER` 同类

白名单理由要写准：不是「未接线」，是「实测该特征不可分」。

### 这次测量的方法论价值

测量（约 1 分钟）就推翻了整个 ② 级的设计。

**教训：ADR 里的数值阈值，如果没有实测支撑，应该默认怀疑。**
这和 spec 024 的「默认值恰好等于硬编码值」是同类问题 ——
都是「看起来合理所以没人验证」。

### 与 016 的关系

016 的 D1（`MemoryEntity` collection 存实体名向量）**作废** ——
不存向量了，不需要新 collection。

016 里的其他内容仍然有效：
- 编辑距离被否定的数据（保留在 020 里）
- `candidate_alias` 池的想法（本次不做，见下）

### 本次不做：`candidate_alias` 人工确认池

016 的 D3 提到「新实体不自动并入，记 candidate_alias 进人工确认池」。

本次聚焦「② 级怎么判」，不做确认池。理由：
- 它是独立的功能（新表 + 管理端点 + 前端）
- 当前的 `alias_reject` 表已经承担了「拒绝记录」职责，再混进去会污染语义
- 先看规则层的准确率，再决定要不要人工介入通道

记录为后续工作。

## 实现记录

### 先测量再决定

016 里「0.92 未必适用」的担心躺了 2 天没验证；14 组对照测量（约 1 分钟）
就推翻了整个 ② 级（数据见 Overview）。

**教训：ADR 里的数值阈值，没有实测支撑就应该默认怀疑。**
和 spec 024 的「默认值恰好等于硬编码值」是同类问题 —— 都是「看起来合理所以没人验证」。

### 五条规则，顺序不能换

`services/entity_match.py`，三态 `SAME` / `DIFFERENT` / `UNKNOWN`：
1 单字前缀冲突 → `DIFFERENT`；2 称呼剥离 → `SAME`；3 后缀白名单 → `SAME`；
4 同义词表 → `SAME`；5 都不中 → `UNKNOWN`（交 LLM）。

**实测踩到的顺序 bug**：`张三哥/张三` 本该走规则 2（称呼剥离→同一人），
但规则 1 先看到「张三 + 哥」判成不同实体，规则 2 永远没机会执行。

修法不是调顺序（1 必须在 3 之前，否则「张三丰」在「丰」进白名单时会被误并），
而是给规则 1 加例外：**多出来的字若是称呼，不算名字冲突**。
两条约束只有这个方案能同时满足，已用两条测试钉住。

### 能力边界写成了测试，不是含糊带过

- `项目A / 项目A组`：都是加后缀但不同实体，**「组」故意不进白名单**
- `阿里 / 阿里巴巴`：全称/简称（「巴巴」不是后缀），只能进同义词表
- `微信 / WeChat`：跨语言，字面零关系

「组」不进白名单的权衡：漏并 = 同实体多一个节点（人工能合）；
误并 = 两实体混成一个（**不可逆**，记忆被污染）。所以宁可漏并。

同义表达（`周会/每周例会` 字面不包含、余弦 0.4806）**任何规则都判不出来**，
只能做成可配置词典。硬写规则去匹配同义，会变成「一堆永远调不完的特例」。

### 接线点与回退

`resolve_one` 里插在 LLM 之前：

```
单字前缀早退（保留）→ 规则层（SAME 直接返回）→ LLM
```

规则判 SAME 时返回 `label=probable, source="rule"` ——
`source` 的这个值在 `AliasClaim` 里**本来就有**，当初就是为规则留的位。

`ENTITY_RULE_ENABLED=false` 时，只有规则 1 保留。这是刻意的：
单字前缀是 spec 020 的独立功能，关掉新规则不该把它一起关掉，
否则就成了「回退到比改动前更差」。

### meta-test：3/3 条测试被证明有效

```
规则层未接线（删掉 best_candidate 调用）  -> 1 failed  ✓
规则顺序错乱（禁用规则 1）                -> 3 failed  ✓
后缀规则过宽（不看白名单）                -> 1 failed  ✓
```

第 2 类尤其重要：规则顺序错时功能「看起来有」，只在特定输入上出错，
是最难靠人眼发现的一类 bug。

### 顺带修了一个真 bug：sweep 调度依赖墙钟

全量跑时 `test_sweep_on_start_false_skips_first_tick` 挂了 ——
它几天前是过的。

原因：`MaintenanceWorker.__init__` 里写的是
`datetime.now(utc) + sweep_every_s`，但 `tick(now=...)` 支持注入时间。
两者混用 = **测试结果取决于今天是几号**。日期一过，注入的 `NOW`
就落到 `_next_sweep_at` 之前，测试必然失败。

修法：`__init__` 不再算时间，改为 `_sweep_pending` 标记；
`sweep_on_start=False` 的第一次 tick 用**传进来的** `now` 起算。

加了一条更硬的回归测试，用 1970 年的时间点 —— 任何依赖墙钟的实现都会立刻失败。

**这类 bug 的启发**：时间可注入的接口，内部就不能再偷偷读墙钟。
否则测试在写的时候是过的，过几天自己挂，而且看起来像「环境问题」。

### 真实数据验证（只读）

66 对真实实体名：判同一 0 / 判不同 2 / 判不了 64。
2 对「判不同」= `上海/上海人`（两个 namespace 各一次）—— **结果对，理由错**：
`split_name_surname` 把「上」当姓，走了「单字名前缀冲突」，日志原因会误导。
spec 020 的既有行为，**记录不扩大范围**。

对照：按向量 0.92，真实数据 18 个名字 **0 对命中** —— ADR 原方案完全不起作用。
（真实数据多为测试残留，收益验证靠 `harness/measure_entity_sim2.py` 的构造对照集。）

### 测试

新增 41 条：37（`test_entity_match.py`）+ 3（`test_alias_prefix.py`）+ 1 墙钟回归。

覆盖重点：四条规则各自命中/不命中、**规则顺序**、关规则层时单字前缀仍生效、
`ENTITY_*=` 显式空即禁用、改配置→行为变、同义词双向且配置写错不炸、
`best_candidate` 可复现（防图抖动）、旧导入路径兼容。

全量：**1133 passed**（1093 + 40）。

零引用：**11 → 10**（`ENTITY_ALIAS_SIM` 理由从「未接线」改成「实测不可分」，
四项新配置全部有消费点）。

### 本次不做

- **`candidate_alias` 人工确认池**（016 的 D3）：独立功能（新表 + 端点 + 前端），
  先看规则层准确率再决定要不要人工通道
- **`ENTITY_ALIAS_SIM` 删除**：保留待换模型重评
- **`split_name_surname` 对地名的误判**：spec 020 的既有行为，已记录
