# 020 实体消歧中间态：单字名前缀保护

## Overview

spec 016 提了一个「中间态」：用**编辑距离**挡住「张三」vs「张三丰」这类误并。
**实测证明这条路走不通。** 本 spec 换成一条更窄但成立的规则。

### 实测：编辑距离的方向是反的

```
A          B            编辑距离   相似度    真实关系
豆包        豆包AI           2     0.50     同人
张三        张三丰           1     0.67     不同人
微信        WeChat          6     0.00     同物
```

关键对比：

- 「豆包」vs「豆包AI」（**同人**）相似度 **0.50**
- 「张三」vs「张三丰」（**不同人**）相似度 **0.67**

**该合并的相似度更低，该区分的更高。** 任何单一阈值都做不到同时满足：

| 阈值 | 张三丰 | 豆包AI | 结果 |
|---|---|---|---|
| 0.6 | 0.67 放行 → **误并** | 0.50 挡住 → **误挡** | 完全反向 |
| 0.4 | 0.67 放行 → 误并 | 0.50 放行 | 等于没做 |
| 0.7 | 0.67 挡住 | 0.50 挡住 | 同物也被挡 |

而且「微信」vs「WeChat」相似度 0.00 却是同物 —— 字面距离对跨语言别名完全无效。

**结论**：编辑距离做不到它声称的事。硬做会做出一个「看起来在工作、
实际把该合并的挡住、该区分的放行」的反向功能。

### 真正可行的窄规则

字面无法区分「张三/张三丰」（像但不同人）和「豆包/豆包AI」（像且同人），
**但有一条可判定的差异**：

- 「张三」是**姓 + 单字名**的中文人名结构
- 「豆包」不是人名（`豆` 不是姓氏）

于是规则：

> 如果 `short` 是 `long` 的**严格前缀**、`short` 是「姓 + 单字名」结构、
> 且 `long` 只比 `short` 多一个字 → 判为**不同实体**，不合并。

验证：

| pair | 判定 | 期望 |
|---|---|---|
| 张三 / 张三丰 | 挡住 | ✅ 不同人 |
| 豆包 / 豆包AI | 放行（豆非姓） | ✅ 同人 |
| 李小狼 / 小狼 | 放行（非前缀关系） | ✅ 同人 |
| 王伟 / 王芳 | 放行（非前缀） | ✅ 不同人（交给 LLM） |

## 非目标

### 不是 C.B3 的三级消歧

只覆盖**一种**可判定情形（单字名前缀）。ADR C.B3 要求的
「① manual alias table → ② embedding 余弦 → ③ LLM 灰区」仍未实现，
spec 016 保持 `planned`。

这个中间态的价值是：**用 20 行挡住最常见、最容易造成实际伤害的一类误并**，
而不是把 C.B3 做完。

### 不落 `alias_reject` 表（本次）

`record_safe` 需要 `namespace` / `event_id`，但 `resolve_one` 的签名里没有这两项。
要把它们传进来需要改签名 + 所有调用点，超出「极低成本」的定位。

本次只做判断 + `logger.info`。**留痕缺失是已知不完整**，理由：
项目的 `alias_reject` 理念是「判错了还看不见才要命」，这条规则挡住了却看不见，
违背该理念 —— 但它的判断更保守（宁可少合并），风险低于原方案。

后续要做的话：把 `namespace`/`event_id` 传进 `resolve_one`，用 `record_safe` 留痕。

### 不动 LLM 那条路的其它部分

白名单校验、置信度阈值、`_label_for` 都不动。只在调 LLM **之前**加一道早退。

## Design

### D1 纯函数：判断是否「单字名前缀冲突」

```python
def single_char_name_prefix_conflict(short: str, long: str) -> bool:
    """`short` 是不是「姓+单字名」，且 `long` 只比它多一个字？"""
```

判据：

1. `len(short) >= 2` 且 `long == short + 一个字`（严格前缀 + 长度差 1）
2. `short[0]` 在姓氏表里（单姓），或 `short[:2]` 是复姓
3. `short` 的名部分长度为 1（单姓时 `len(short) == 2`；复姓时 `== 3`）

### D2 复用现有姓氏表

`labeler._COMMON_SURNAMES` 已经覆盖单姓 + 复姓，且项目里有
`declared_surnames()`（用户声明的额外姓氏）。

`alias_resolver` 不 import `labeler`（会引入不必要的耦合？）——
需要评估：`labeler` 是否已经 import 了 `alias_resolver` 依赖的东西。

若循环依赖，就把姓氏集合作为参数传入，或提到 `core/` 下。

### D3 在 `resolve_one` 里早退

```python
for cand in allowed:
    if single_char_name_prefix_conflict(claim.alias, cand):
        logger.info("单字名前缀冲突，不合并 | %s vs %s", claim.alias, cand)
        return None
```

放在**调 LLM 之前**，省一次调用。

### D4 方向要双向检查

`claim.alias` 可能是长的那个（「张三丰」是别名，「张三」是候选）。
所以两个方向都要判：`(alias, cand)` 和 `(cand, alias)`。

## Notes

### 为什么「长度差 1」而不是「长度差 ≤ 2」

「张三」vs「张三丰丰」这种四字名有歧义（可能是同一人的昵称）。
只挡差 1 的（最典型的人名扩展），保守。

### 这条规则会误挡什么

「李雷」vs「李雷雷」—— 如果真的是同一人（昵称），会被挡住。
代价：少合并一次，可以人工在后处理里补。

方向是**宁可少合并**：误合并会污染图谱（两个人变成一个人，之后所有查询都错），
误挡只是少一条别名边（信息缺失但不会错）。

这与项目现有取向一致：`alias_reject` 的注释写「判错了不要紧，判错了还看不见才要命」。

### 为什么不做「编辑距离 + 姓氏」的组合

可以把姓氏当作编辑距离的修正项，但实测显示同人/不同人在距离上重叠，
加修正系数只是把阈值问题藏起来。**用一个可解释的规则，比用一个调不出好数的评分好。**

## 实现记录

### 最重要的发现：原方案（编辑距离）方向是反的

spec 016 提的「中间态」是用编辑距离挡住「张三 / 张三丰」。动手前先验了一下：

```
A          B          编辑距离  相似度   真实关系
豆包        豆包AI         2    0.50    同人
张三        张三丰         1    0.67    不同人
微信        WeChat        6    0.00    同物
```

**该合并的相似度更低（0.50），该区分的反而更高（0.67）。**

任何单一阈值都做不到：

| 阈值 | 张三丰(0.67) | 豆包AI(0.50) | 结果 |
|---|---|---|---|
| 0.6 | 放行 → 误并 | 挡住 → 误挡 | 完全反向 |
| 0.4 | 放行 | 放行 | 等于没做 |
| 0.7 | 挡住 | 挡住 | 同物也挡 |

如果照着原 spec 实现，会做出一个「把该合并的挡住、该区分的放行」的反向功能 ——
**比不做更糟**，因为它看起来在工作。

这条数据被固定成了测试 `test_edit_distance_is_reversed_for_these_pairs`，
并配了一段说明：如果将来这组数据变了，才值得重新讨论距离阈值方案。

### 换成什么：中文人名结构

字面距离无法区分这两类，但**结构**可以：

- 「张三」是「姓 + 单字名」
- 「豆包」不是人名（`豆` 不是姓）

规则：

```
short 是「姓+单字名」 且 long 只比它多一个字  →  判为不同实体
```

判据（`labeler.split_name_surname`）：

| 输入 | 姓 | 说明 |
|---|---|---|
| 张三 | 张 | 单姓 + 单字名 |
| 欧阳锋 | 欧阳 | 复姓 + 单字名 |
| 李小狼 | None | 单姓 + **双**字名 |
| 豆包 | None | `豆` 不是姓 |

验证：

```
张三/张三丰     -> True   挡住 ✅
豆包/豆包AI     -> False  放行 ✅
李小狼/小狼     -> False  放行 ✅
欧阳锋/欧阳锋儿 -> True   挡住 ✅
张三/张三丰丰   -> False  长度差 2，保守放行 ✅
```

### 复姓表没有重复定义

`labeler._COMMON_SURNAMES` 是一个大字符串，复姓混在里面，无法可靠切分。
所以在 `labeler.py` 里加了 `COMPOUND_SURNAMES` 常量和 `split_name_surname()` 函数，
作为「姓氏结构判定」的单一源头，`alias_resolver` 直接复用。

没有在 `alias_resolver` 里另写一份复姓表 —— 重复定义会漂移。

### 双向检查

`claim.alias` 可能是长的那个（「张三丰」是别名，「张三」是候选），
所以两个方向都判：

```
single_char_name_prefix_conflict(claim.alias, cand)
  or single_char_name_prefix_conflict(cand, claim.alias)
```

### 在调 LLM **之前**早退

放在 `allowed` 计算之后、`_build_prompt` 之前。省一次 LLM 调用，
也不给模型误判的机会。

### 测试里踩到两个坑（都会让测试假通过）

**① patch 目标错了**

`alias_resolver` 里是 `from memory.services.llm import chat` ——
`chat` 这个名字绑在**它自己的模块命名空间**里。
patch `llm_mod.chat` 对它完全无效。

后果：`test_resolve_one_skips_llm_on_conflict` 期望 `calls == 0`，
而 patch 无效时**实际也是 0**（因为真 LLM 因为没网络失败了）——
**测试假通过**。

修法：`monkeypatch.setattr(alias_resolver, "chat", fake)`。

这条被「不冲突时应该 calls == 1」那条测试暴露出来 ——
如果只写「挡住时 calls == 0」，两个测试都会假通过。

**又一次验证了「必须有反向断言」**（017 也是这个教训）。

**② 假 LLM 返回了候选外的名字**

`resolve_one` 有白名单校验：返回的名字必须在 `allowed` 里，否则丢弃。
第一版假 LLM 固定返回 `张三丰`，测试用 `豆包`/`豆包AI`，
于是被白名单丢掉，`got is None` —— 看起来像「规则挡住了」，其实是白名单干的。

修法：假 LLM 接受 `pick` 参数，返回候选里的名字。

### 这条规则的代价（已知）

「李雷 / 李雷雷」若真是同一人（昵称），会被挡住。方向是**宁可少合并**：
