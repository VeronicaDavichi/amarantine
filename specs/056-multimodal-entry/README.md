# 图片理解只走实时入口，历史灌入不追溯

## Overview

**主人定的架构边界**（2026-11-28）：

> 这个口子预留给类似 OneBot 的产物，所以只会在实时信息进来的时候接入保存动作，
> 而不是灌历史消息的时候。

也就是把「多模态」这件事**按入口分流**：

| 入口 | 图片怎么处理 | 状态 |
|---|---|---|
| **实时消息**（OneBot 类网关） | 收到就做**保存动作**：下载 → 视觉概括 → 文本化入库 | ⬜ 预留，未接 |
| **历史灌入**（`/admin/ingest`） | 只存 `[图片] <HASH>.png` 占位符，**不追溯** | ✅ 现状即终态 |

## 为什么要这样分（实测支撑）

### 历史图片基本拿不到

想给历史消息补图，前提是从 `[图片] HASH` 定位到文件。实测（namespace
`qq-10000000001-v2`，9112 条原文）：

| 项 | 值 |
|---|---|
| 消息里的图片哈希（去重） | 2938 个 |
| QQ 图片缓存文件 | 54103 个（16 GB） |
| 能按哈希对上 | **28 个（1.0%）** |
| 且能对上的集中在 2026-04（那个月只有 135 个文件） | 说明是巧合 |

`Pic/YYYY-MM/Ori/<md5>.<ext>` 的文件名与消息里的 `[图片] HASH` **不是同一个标识**。
1% 的匹配率不足以支撑任何补救方案。

### 成本与收益也不划算

| 项 | 数量 |
|---|---|
| 含图片的消息 | 1416（15.5%） |
| · **纯图片（无文字）** | **820** |
| · 图文混合 | 596 |
| 只含表情/视频、无图片 | 1178 |

820 条纯图片 × 约 1300 视觉 token ≈ **107 万 token**，而其中大量是表情包、
贴图、商品图 —— 花这个钱去猜「这张图说了什么」，性价比远低于**在实时入口
拦住它、当场概括**。

### 实时入口天然有优势

收到消息的那一刻：

- 图片 URL / 文件句柄就在手上（不需要反查哈希）
- 时间、发送者、上下文都是新鲜的（概括更准）
- 只处理真正到达的消息，不用赌「历史上那些图还在不在」
- 概括失败可以立刻重试或降级，不影响任何存量数据

## Design

### 保存动作（实时入口的定义）

一次「图片保存动作」= 三步，任何一步失败都**降级为占位符**而不是丢消息：

```
收到消息（含图片）
  → 1. 取图：从网关给的文件/URL 拿到二进制
  → 2. 概括：视觉模型 + 上下文，产出一句中文描述
  → 3. 文本化：把描述写进 raw_quote.text
```

### 关键设计：**概括结果写进 text，不新增字段**

```
现在：  运营：[图片] 8FDD64B8CFBABFA7BB865AFDAA19AD1C.png
以后：  运营：[图片：本日开启尾款，附图是 Fate FSF 的徽章与立牌]
```

**为什么不加字段**：

| 加字段的方案 | 写进 text 的方案 |
|---|---|
| 切分、摘要、向量、BM25 四层都要改 | **四层一行都不用改** |
| 要改 schema + 重灌 | 只是写 text 时多拼一段 |
| 召回材料要新增返回字段 | 现有 `raw_quotes` 直接就有 |

图片的描述本质上就是「这条消息的文字内容」——它就该待在 `text` 里。
这也与 spec 055 的教训一致：**信息该在的地方就放在那，别让下游猜**。

### 降级链（三级，不许丢消息）

| 情况 | 写入什么 |
|---|---|
| 取图成功 + 概括成功 | `[图片：<描述>]` |
| 取图成功但概括失败（超时/模型不可用） | `[图片] <hash>.<ext>`（现状占位符） |
| 取图失败（URL 过期/文件没了） | `[图片]`（连 hash 都没有，因为本来就没有） |

**顺序固定**：先落原文（带占位符）→ 再异步补描述。
这样即使进程被杀，消息也不会丢，只是图没被概括。

### 入口形态（预留，不现在实现）

实时入口不在本 spec 实现，但定清它的形状，避免以后接的时候改数据模型：

```
POST /admin/realtime            # 单条消息即时入库（同步返回 quote_id）
{
  "namespace": "qq-...",
  "session_id": "...",
  "role": "user",
  "ts": "2026-11-28T19:00:00+08:00",
  "text": "...",
  "images": [{"url": "https://...", "hash": "..."}]   # 可选
}
```

与 `/admin/ingest` 的区别：

| | `/admin/ingest` | `/admin/realtime` |
|---|---|---|
| 批次 | 多条 + 异步 job | 单条 + 同步 |
| 用途 | 历史灌入 | 实时消息 |
| 图片 | 忽略（只存占位符） | 走保存动作 |
| 幂等 | `dedupe_key` | `quote_id` 本身（内容哈希） |

**为什么单条同步**：实时场景要「发完就记得」，异步 job 的排队延迟不可接受；
单条的切分成本低（几条消息），同步跑得动。

## Notes

### 这条边界为什么重要

它避免了一个典型的过度设计：**为了 15.5% 的图片消息，去改四层管道、加字段、
重灌语料**，而其中真正有信息量的可能不到三成。

按入口分流之后：

- 历史数据保持现状（占位符，不追）
- 新消息在到达时把图的语义**一次性榨干**，文本化后进入现有链路
- 召回、摘要、向量、BM25 四层**不需要知道「有图片这回事」**

这是「在正确的层解决问题」的典型：图片是**输入形态**问题，不是存储/检索问题。

### 不做什么

| 不做 | 理由 |
|---|---|
| 追溯历史图片 | 1% 可定位率，代价与收益完全不成比例 |
| 多模态向量（图片直接进向量库） | 意味着新增一路索引 + 改召回 + 改 rerank；文本化已经把语义榨出来了 |
| 图片单独存为一张卡 | 图片是某条消息的**内容**，不是独立事件；拆开会破坏「谁说了一句什么」 |
| 视觉概括同步阻塞 `/admin/ingest` | 历史灌入不该被视觉模型拖慢，且历史图本来就拿不到 |

**真实调用验证（3 张真实图片 + 真 LLM）**

| 版本 | 结果 |
|---|---|
| `IMAGE_CAPTION_MAX_TOKENS=320` | **1/3 成功** |
| `IMAGE_CAPTION_MAX_TOKENS=1500` | **3/3 成功** |

失败原因是带 thinking 的模型把思考算进 `max_tokens`，320 让「想完就没额度输出」，
直接空返回（错误信息：`没有返回文本（可能被 max_tokens 截断在 thinking 阶段）`）。
已把默认值调到 1500 并在配置注释里写明，避免有人「优化」回去。

耗时 1.8–5.3 秒/张，对实时入口可接受。

**实现中改掉的一个设计错误**

第一版设计是「先落占位符版本 → 概括后替换文本 → 重算 quote_id」。
问题：`quote_id` 由文本哈希决定，替换后 id 变了 ——
**同一条消息重发会因为「概括是否成功」落到不同 id，幂等直接破掉**。
而且需要存储层新增 `replace_text`（不该为这个加）。

改成**先概括、再算 id、一次写入**。代价是这条路径慢 2–5 秒，
换的是 id 稳定 + 存储层不用动。

**隐私处理**

端到端验证脚本原本会把概括正文打到终端。缓存里是真人私照与带敏感文字的截图，
打出来等于二次留存。已改成只输出「成功/长度」，不输出正文。

**测试基线**：1737 passed（含新增 26 条），零回归。

**顺带修的测试脆弱性**

`tests/test_recall_budget.py` 从 `.env` 读设置，我在 `.env` 里开了
