# 关系谓词：从「事件牵涉了谁」到「谁和谁是什么关系」

> **Status**: draft · **Priority**: medium · **Created**: 2026-11-06

## Overview

**问题**：图上的关系只有挂载式边，没有谓词。

```
节点：Event 740 · Entity 41 · Person 40
边  ：RELATED 12640 · INVOLVES 848 · AT 743 · ACTION 92 · MENTIONS 91 · ALIAS_OF 1
人 → 人 的边：0
人 → 非 Event 的边：0
```

问「王勇跟谁对接」「谁负责前端」，**没有边可走**，只能靠共现猜。
而 `RELATED` 占了全部边的 92%（平均每事件 17 条），关系预算花在了事件纠缠上。

**目标（粗）**：定义业务谓词表，让「人—关系—人/实体」这类边可被抽取、可被查询。

**非目标**

| 不做 | 理由 |
|---|---|
| 引入推理机（RDFS/OWL/Datalog） | 缺的是边不是推理；触发条件见 Notes |
| 改事件卡粒度 | 卡的精度是 P0 已定项，上下文走窗口输入而不是塞进卡 |
| 跨 namespace 合并实体 | 不在本 spec 范围 |

## Design

### 谓词表（草案，待细化）

| 谓词 | 头 | 尾 | 例 |
|---|---|---|---|
| `OWNS` | Person | Entity/Project | 王勇 --负责--> 反洗钱前端 |
| `MAINTAINS` | Person | Entity/Service | 成善明 --维护--> ESB |
| `REPORTS_TO` | Person | Person | 待定（语料里目前没有直接证据） |
| `COLLABORATES_WITH` | Person | Person | 刘佳媚 ↔ 刘阅（同场处理同一客户） |
| `DEPENDS_ON` | Entity | Entity | aml-scripts --依赖--> 中登接口 |

约束：头尾类型固定；每条边带 `evidence_count` 与 `source_event_ids`（可回溯）。

### 上下文窗口（待验证）

单句摘要里关系常跨句成立（「王老师那边」+「他负责前端」），所以抽取输入要带窗口：

```
窗口 21 条（±10），stride 10（50% 重叠）
```

重叠会让同一关系被抽多次 → **边用 `MERGE (h)-[r:PRED]->(t)` 合并**，累加证据。
这点比卡片友好：卡片重复是灾难，边重复只是 MERGE。

### 与 038 的耦合

窗口抽出来的人名仍是称呼形态（`王老师`）。038 不做，边会连到假人节点，
**关系越丰富错得越多** —— 所以 038 应排在本 spec 之前。

## Notes

### 为什么暂不引入推理机

短答：**缺的是边，不是推理**。推理机的输入是已知事实，而现在人-人边为 0。

现在的三类「推理」，两类用 Cypher 就够：

| 需求 | 手段 |
|---|---|
| 路径/传递（别名、上级链） | `[:ALIAS_OF*0..1]`、`shortestPath` —— Neo4j 原生 |
| 写入期物化（同项目=>协作者） | 定时 Cypher 落成边 |
| 类型包含 / 一致性 / 可解释 | 这才需要推理机 |

**引入触发清单**（中三条再谈）：

1. 规则需链式组合且频繁变化，Cypher 维护不动
2. 多来源实体合并需要冲突检测
3. 查询里大量「间接关系」（间接汇报/持股/依赖）
4. 需要解释「结论由哪些规则推出」（审计场景）
5. 关系类型 > 50 且存在类型层级

另外，ADR-001 对别名已表态：*「用户直接给了等价关系，不用推理」「别名表是可复查的事实，模型推理不是」* ——
引入推理机等于反转这个取向，得有强理由。
