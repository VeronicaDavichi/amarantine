# 021 清理记忆脏数据并重建真实卡

## Overview

排查「孤岛降权」时发现，`work` 命名空间的数据是**不可用的**：

```
卡片 53 张 → 50 张是冒烟测试残留（94%）
图 59 个 Event → 度数分布 {0: 19, 1: 40}，最大度数 1
实体边（MENTIONS/INVOLVES）：0 条
唯一边类型：AT→Time  40 条
entity_names：1 张是句子片段 '张三决定项目'，51 张为空
```

三层原因：

1. **数据层**：50 张 `e2e-xxx` 冒烟测试标记，本不该留在生产 namespace
2. **因果层**：10-31 写入时实体抽取产出句子片段 → 建图按名字找不到 Entity → 不建边
3. **架构层**：`event_id` 哈希含 `entity_names`（ADR D1），重算会改 id

本 spec 只做**清理和重建**。孤岛降权（用户原始需求）依赖健康数据，不在本 spec。

## Design

### D1 删除的边界：事实层软删，索引层物理删

| 层 | 处理 | 依据 |
|---|---|---|
| 事件卡（Weaviate） | **软删** `is_deleted` + `deleted_at` | D7/A9：事实层永不物理删 |
| 图节点（Neo4j） | **DETACH DELETE** | D2：图可丢弃重建，是索引 |

现有 `forget_event()` 只软删卡片 + 让图节点改 `retention`，**不删节点**。
所以清理脚本要在软删之后**额外删图节点** —— 否则 50 张卡变成「软删但图里还在」，
度数统计照样被污染，孤岛信号仍然无效。

### D2 判定「测试残留」的规则

保守：只认显式标记，不做启发式猜测。

```
summary 含 e2e- / 冒烟测试 / 迁移验证 / 验证标记
```

不按 namespace 判定（`work` 是真实 namespace，只是混进了测试数据）。

### D3 孤儿节点：图里有、卡片没有

图 59 个 Event vs 卡片 53 张，差 6 个。这些是卡片已删但图节点残留的。
一并清掉。

### D4 重建 3 张真实卡

原始内容（从现有卡片读出）：

| summary | types |
|---|---|
| 张三决定项目A延期到六月 | decision, work |
| 李四确定了新项目B的启动时间 | decision, work |
| 周会上讨论了明年的预算分配方案 | money |

走完整 `remember_event()` 流程（不是手写 Weaviate），理由：
去重、图写入、别名、事件 id 全部走一遍，避免手工拼装漏步骤。

**event_id 会变**（用户已确认接受）：旧 id 基于 `'张三决定项目'` 这个垃圾实体名，
新 id 基于 `'张三'` + `'项目A'`。只有 3 张，影响可控。

**副作用（已知）**：`ingested_at` 变成当前时间 → 这 3 张卡的 freshness=1.0，
在遗忘策略里进入宽限期。会被日志和本 spec 记录，不假装没有。

### D5 必须 dry-run

删除不可逆（图节点物理删）。脚本默认 dry-run，`--execute` 才动手。

### D6 留痕

每次软删带 `reason`（用 `ALLOWED_REASONS` 里的 `outdated` 或 `user_forget`）。
脚本输出一份清单：`event_id` / `summary` / 动作，供事后审计。

## Notes

### 为什么不在这个 spec 里做孤岛降权

用户的原始需求是「孤岛数据降低重要性」。当前数据下这个信号**无区分度**
（59 个节点全是孤岛）。先清数据，孤岛信号才有意义。

顺序不能反：**在垃圾数据上调参数，只会调出垃圾的参数。**

### 这个发现值得记一笔

`GRAPH_HUB_DEGREE = 8` 的保护**从来没有生效过** —— 图里最大度数 1。
这是第 8 起「配了但不起作用」，但性质不同：前七起是代码没接线，
这起是**数据不支持**。

说明「配置是否生效」的检测还缺一个维度：不只查「有没有消费点」，
还要查「消费点有没有拿到过非零值」。

## 实现记录

### 执行前的关键发现：直接重建会变成 6 张

去重是按 `event_id` 查的（`remember_event` → `get_by_event_id`）。
重建后 `entity_names` 变了 → `event_id` 变了 → 查不到旧卡 → **新建一条**。

旧卡如果留着，就是 3 旧 + 3 新 = 6 张重复内容。

所以「重建」的正确语义是：**旧卡软删留痕 + 新卡写入**。
不是「就地更新」。

设计从「软删 50 张测试卡」改成「软删全部 53 张 + 图节点全清 + 重建 3 张」。

### 第二个发现：`remember_event` 没有 types 参数

签名里没有 `types`，打标由内部打标器完成。所以重建是**重新处理**，
不是**恢复原样** —— types 会重算。

实际结果出乎意料地好：3 张卡的 `types` 与原来**完全一致**
（`['decision','work']` / `['decision','work']` / `['money']`），
说明打标器对这类文本是稳定的。

### 执行结果

```
① 软删卡片：53 成功，0 失败（reason=outdated）
② 删图节点：59 个（含 6 个孤儿）
③ 重建：3 张，全部成功
```

1. **`ingested_at` 变成当前时间** → 3 张卡 freshness=1.0，在遗忘策略里进宽限期。
   这是走 `remember_event` 完整流程的代价。
2. **53 张软删卡仍在 Weaviate**（D7/A9 事实层永不物理删）。
   召回会过滤 `is_deleted`，但**健康度检查必须自己过滤** ——
   第一版 `check_data_health.py` 没过滤，报出「56 张卡、89% 测试残留」的假警报。
3. **`GRAPH_HUB_DEGREE=8` 依然没生效**（最大度数 5）。

### 教训

**「配置是否生效」的检测还缺一个维度。**

前七起「配了但没起作用」都是代码没接线，用零引用检测就能抓到。
这起不一样：`GRAPH_HUB_DEGREE` **有消费点、有测试、代码正确**，
只是**数据里没有能触发它的值**。

零引用检测永远抓不到这一类。

要抓它，需要的是「消费点拿到的输入分布」——比如「这个阈值有没有被跨过过」。
这比计数复杂得多，但至少这次踩到的坑值得记下来。
