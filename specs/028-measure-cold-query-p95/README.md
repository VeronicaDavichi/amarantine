# 028 实测冷查询 P95 并接线告警

## Overview

`COLD_QUERY_P95_MS = 800` 是 ADR 里唯一一个「写了目标、从未验证」的指标。

### 现状：完全没有测量手段

```
recall.py 里 perf_counter: 0 次   time.monotonic: 0 次
          elapsed: 0 次          duration: 0 次
harness/ 里没有任何性能脚本
```

更讽刺的是 **`VECTOR_TIMEOUT_MS` 的注释写着「默认 800ms，与
`COLD_QUERY_P95_MS` 对齐」** —— 也就是说，一个从未被测量的目标，
被当成了另一个参数的取值依据。

这和 026 是同一类问题：**ADR 里的数字，没有实测支撑就应该默认怀疑**。

### 这次要回答两个问题

1. **现在真实是多少？** —— 不知道，因为从来没量过
2. **800 这个目标合理吗？** —— 量完才知道

## Design

### D1 埋点：总耗时 + 分通道耗时，只在结束时算一次

在 `recall()` 里：

```
t0 = time.monotonic()
... 各通道并行 ...
total_ms = (time.monotonic() - t0) * 1000
```

分通道耗时用 `future.result()` 返回后补记 —— **不能**在各通道函数内部
加计时后相加（并行时相加是错的，只有最慢的那个决定总时长）。

`time.monotonic()` 而不是 `time.time()`：后者会被系统时钟调整影响，
测量时长必须用单调时钟。

**埋点必须在 `finally` 里也能取到值**，否则抛异常时测不到耗时 ——
而慢查询恰好可能以超时异常结束。所以 `t0` 在函数最开头就要取。

### D2 超阈值告警：让配置有真实消费点

```
if total_ms > settings.COLD_QUERY_P95_MS:
    logger.warning("冷查询耗时超目标 | %.0fms > %dms | 通道: ...", ...)
```

这样 `COLD_QUERY_P95_MS` 有了消费点，且满足「改配置 → 行为变」：

- 设成 `1` → 几乎每次查询都告警
- 设成 `999999` → 永不告警

**不是**「记录 P95 然后比较」——单次查询不知道自己是不是 P95。
用「单次超目标就告警」是对的：P95 是**统计结果**，告警是**单次事件**，
两者的关系是「P95 达标 ⟺ 95% 的查询不告警」。

### D3 `<= 0` 关闭告警

沿用项目惯例（`GRAPH_HUB_DEGREE=0` 关信号、`TIME_CONF_MIN<=0` 关闸门）：

`COLD_QUERY_P95_MS <= 0` = 不告警。

不能让它变成「0ms 目标，每次都告警」—— 那会让日志被淹。

### D4 测量脚本：N 次**不同 query**，算 P50/P95/P99

```
python ../harness/measure_recall_latency.py --n 30
```

要点：

1. **每次用不同 query** —— 同一个 query 会被 Weaviate / embedding 侧的
   缓存热化，量出来不是冷查询
2. **先跑一次丢弃**（warmup），它的目的是把连接池、DNS、模型加载等
   一次性开销吃掉；剩下 N 次才算样本
3. 报告 **P50 / P95 / P99 / min / max / 均值**，以及**分通道耗时分布**
4. 同时报告**是否触发告警**，用来验证 D2 真的生效

### D5 只测「暖启动后的冷 query」，不测「进程冷启动」

真·冷启动（进程刚起、连接池空、embedding 模型未加载）的第一查可能几秒。
但那不是 P95 要管的场景 —— 它每次都只发生一次。

所以：warmup 1 次 → 测 N 次。**在报告里明确说明这一点**，
避免有人拿这个数去和「服务刚重启时的首查」比较。

### D6 不改 `VECTOR_TIMEOUT_MS`

它的注释说「与 COLD_QUERY_P95_MS 对齐」，但**这是 ADR 的设计意图**，
不是这次的测量结论。量完如果发现 800 不合理，应该改 ADR + 两个值一起动，
而不是单方面改一个。

**本次只测量 + 告警，不动任何超时值。**

## Notes

### 为什么这条值得单独一个 spec

它不改任何业务逻辑，看起来像「加日志」。但它回答的是
**「ADR 写的 800 到底对不对」** —— 而这个问题从 ADR 定稿起就没人问过。

026 的教训是「阈值没有实测就该怀疑」。028 就是把这条教训用到
**唯一一个还没被检验过的数字**上。

### 如果实测远超 800 怎么办

**不改 800，先记录差距和分通道耗时**。

理由：单次测量不足以定新目标（数据量太小、可能受机器负载影响）。
正确顺序是「先有测量手段 → 持续观察 → 有分布后再定目标」。

本次的交付物是**测量能力 + 告警**，不是「把 800 改成 3000」。

### 与 `RECALL_BUDGET_MS` 的关系

`RECALL_BUDGET_MS=1500` 是**运行时预算**（超了就降级返回 partial）。
`COLD_QUERY_P95_MS=800` 是**性能目标**（超了只告警，不影响返回）。

两者不是一回事：预算管「别让用户等太久」，目标管「我们够不够快」。
接线时不能混用 —— 用 `RECALL_BUDGET_MS` 做告警阈值，
那 95% 的查询永远不告警（因为超预算的已经被截断成 partial 了），
告警就失去意义。

## 实现记录

### 三轮实测：800 处于临界

| 轮次 | 样本 | P50 | **P95** | P99 | max | 800 目标 |
|---|---|---|---|---|---|---|
| 1 | 20 | 547.6 | **671.1** | 708.2 | 717.5 | ✅ 余量 129 |
| 2 | 50 | 636.8 | **878.5** | 934.5 | 956.4 | ❌ 超 78.5（1.10×） |
| 3 | 50 | 594.5 | **739.1** | 785.3 | 802.5 | ✅ 余量 61 |

**结论不是「达成」也不是「超标」，是「贴着目标波动」。**

P95 在 671–878ms 之间，中心约 730–750ms。失败那轮（第 2 轮）的 P50 也最高
（636.8），说明是**整机负载波动**而非单次偶发长尾。

这也解释了为什么 20 次测出「达成」而 50 次测出「未达成」：
**20 次样本的 P95 不稳，不足以判定。** 如果只跑 20 次就写「已验证」，
那就是又一个「看起来有数据其实没数据」的 026 式错误。

### 最重要的发现：520ms 不在检索上

分通道耗时（50 次样本）：

| 通道 | P50 | P95 | max |
|---|---|---|---|
| vector | 24.5 | 35.6 | 49.4 |
| bm25 | 19.8 | 33.2 | 43.0 |
| graph | 22.3 | 41.1 | 47.7 |

三个通道并行，总耗时由最慢者决定 —— **约 30–50ms**。

而 P50 是 547–637ms。**也就是说整次 recall 有 90% 以上的时间不在检索上。**

cProfile 定位：

```
rerank()                                      314 ms/次   ← 最大单一开销
_default_embedder                             178 ms/次
httpx.Client.__init__ → create_ssl_context     33 ms × 3/query
```

第三项是**纯浪费**：`embedding.py:48` 和 `rerank.py:92` 都写成
`client or httpx.Client(...)`，每次 recall 新建 3 个 client（embedding /
rerank / WeaviateStore），**每次都重新 `load_verify_locations` 加载 CA 证书**。
约 100ms/query，占 P50 的 15% 以上。

**没修**：超出 028 范围（本次交付物是测量能力 + 告警）。复用 client 涉及
并发安全、超时语义、以及「单例还是连接池」的选择，属于要单独决策的事，
不该顺手改。

### 我自己写的埋点也错了，被 meta-test 抓住

第一版把通道耗时记在 `for name, future in futures.items()` 里。`wait()` 返回时
所有已完成的 future 都完成了，遍历又是顺序的 —— 三个通道拿到**同一个值**：

```
bm25   P50=25.5  P95=271.3  max=362.3
graph  P50=25.5  P95=271.3  max=362.3     ← 三个一模一样
vector P50=25.5  P95=271.3  max=362.3
```

那条埋点测的是「遍历顺序」，不是通道耗时。改成各线程内 `_timed` 包装后才对。

**meta-test 的第一版注入也没抓到它** —— 我把 `started` 改成 `t0` 来模拟，
但 fake 里 embedding 是 0ms，`started - t0 ≈ 0`，行为几乎没变，测试照样过。
改成注入了固定值 `42.0` 才真的能证明测试有效。

**教训叠了一层**：埋点会写错，测埋点的 meta-test 也会写错。
两边都必须验证「注入真的改变了行为」。

### 白名单自动过期，机制生效了

接上消费点后，`test_whitelist_entries_are_still_unused` 立刻报：

```
这些字段已经有消费点了，请从 WHITELIST 删掉：
    COLD_QUERY_P95_MS
```

白名单不是一次性文档，是会**自己过期**的断言 —— 这正是它比注释强的地方。
零引用字段从 10 降到 9 项（`COLD_QUERY_P95_MS` 出列，`GUIDE_CHECK_CRON`
的理由在 027 里改准了但仍是「有意不接」）。

### `test_budget_caps_total_time` 偶发失败（既有问题）

全量第一次跑：`1 failed, 1145 passed`，失败的是
`test_budget_caps_total_time`（用时断言 `ms < 700`）。

单独连跑 6 次全过，第二次全量 1146 全过。**是全量跑 146 秒到它时机器负载高
导致的偶发**，不是 028 引入的（我的改动只加了纳秒级的 `monotonic()` 调用）。

**记录不修**：要修得把 `ALLOWED_MS` 从 700 放宽，或改成「相对慢通道耗时的
比例」而非绝对毫秒 —— 那是另一个 spec 的事。而且放宽时间断言会削弱
「预算真的生效」的检测力，需要想清楚。

### 为什么告警放 `finally` 而不是 `return` 前

慢到超时抛异常的查询**也是慢查询**，而且是最需要被看见的那批。
`WeaviateStoreError` 会变成 503，那条路径不经过 `_finish` ——
告警放 `return` 前就会漏掉它们。`test_elapsed_available_when_channel_raises`
钉住这一点。
