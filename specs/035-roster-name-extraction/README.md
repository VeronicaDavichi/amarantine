# 035 用权威名册提取人名，不再让 jieba 猜

## Overview

灌 DingTalk 真实数据时发现：`extract_entities("孙柏林")` 返回 `("person", "柏林")`
—— **姓氏「孙」被吃掉了**。

根因是 jieba 分词：

```
jieba: '孙柏林' → [('孙', 'zg'), ('柏林', 'nr')]
                    ↑ 状态词（丢掉）   ↑ 人名（收下）
```

「柏林」是德国首都（jieba 词典里有），于是「姓 + 地名」被拦腰切开。

### 影响面实测：14 个人名里 7 个坏的

| 人名 | 提取结果 | 坏法 |
|---|---|---|
| 孙柏林 | `柏林` | 吞掉姓氏 |
| 刘北京 | `北京` | 吞掉姓氏 |
| 陈上海 | `上海` | 吞掉姓氏 |
| **李长春** | **`[]`** | **整个人消失** |
| **李向前** | **`[]`** | 整个人消失 |
| **王光明** | **`[]`** | 整个人消失 |
| **赵和平** | **`[]`** | 整个人消失 |
| 张家界 | `张家界`（当人名） | 反向误判 |

两种坏法里，**「整个人消失」最严重** —— 那个人在所有记忆里都不存在，
不是名字不对的问题。

「姓 + 常见双字词」是个很大的集合（城市名、褒义词、时间词），
不是少数怪名字。

## Design

### D1 用户给的方向：名册里出来的都是名字

> 「这个名字是某个人的 id，备注，什么的，从这个信息出来的都是名字」

**数据源本来就有权威名册**，不需要用分词去猜：

| 来源 | 内容 | 可信度 |
|---|---|---|
| `list_dingtalk_contacts` | `uid → nick` | **权威**（平台同步的联系人） |
| 群标题 | `孙柏林,王勇,任泽昂,王婕` | **权威**（群成员名单） |
| 消息的 `sender_name` | 每条消息的发言人 | **权威**（平台给的显示名） |

从这三处拿到的字符串**就是人名**，不存在「猜错」的可能。

### D2 机制：注册名册 + 最长匹配优先

仿照已有的 `register_surnames` / `_DECLARED_SURNAMES`（同一个文件里就有这个模式）：

```
register_roster(names: Iterable[str]) -> int   # 返回新增几个
reset_roster()                                  # 清空（测试用）
roster_names() -> frozenset[str]                # 只读快照
```

`extract_entities` 改成**两段式**：

```
1. 名册匹配（最长优先）
   - 在文本里找所有出现在名册中的名字
   - 同一个位置有多个候选时取最长（「孙柏林」优先于「柏林」）
   - 命中的直接收为 person，**并把这些片段从文本里挖掉**
2. 剩下的文本再走 jieba 分词（原有逻辑不变）
```

**「挖掉」是关键**：不挖掉的话，jieba 还会在剩余文本里再抽一次
「柏林」，导致同一个人出现两条记录（`孙柏林` + `柏林`）。

### D3 名册不能替代 jieba，只能优先

名册是**不完备的**：文本里可能出现没在名册里的人（第三方、外部厂商）。
所以名册匹配完之后，剩余文本**继续走 jieba**，不是直接跳过。

**顺序**：名册 > jieba。不是「有名册就不用 jieba」。

### D4 名册是运行时状态，不是配置

和 `_DECLARED_SURNAMES` 一样放模块级变量，通过函数注册。

**为什么不做成配置项**：名册可能有几百上千个名字，写进 `.env` 不现实；
而且它是**数据源相关**的（DingTalk 的名册对别的数据源没意义）。

灌数据脚本负责在开始前注册名册。

### D5 「张家界」这类真地名要防住

名册里如果有「张家界」（真的是个人叫这名字），那它就该被当人名 ——
**名册优先于 jieba 的地名判定**，这是对的。

但反过来：**名单里没有的词，不能被名册机制误收**。
所以「张家界」在没有名册时仍走 jieba（现在被判成人名，这是 jieba 的问题，
不在本 spec 范围 —— 本 spec 只解决「名册里有的名字」）。

**范围边界**：本 spec 只保证「名册内的名字提取正确」，
不试图修复「名册外的人名靠 jieba 猜错」的问题。

## Notes

### 为什么这个比「修 jieba 切分」对

修 jieba 切分是**对抗一个通用分词器**，要穷举「姓 + 什么词」的组合，
永远有漏网的。

名册是**绕过分词**：既然平台已经告诉了我们这些人叫什么，
为什么还要用一个通用词典去猜？

这和 026 的教训是同一个：**有确定性信息时，不要用概率模型去猜**
（那次是「用户配了同义词就不要让规则 1 抢」，这次是「平台给了名册就不要让 jieba 拆」）。

### 名册的时效性

名册是**灌数据那一刻**的快照。之后新加的人不在名册里 —— 那会走 jieba
（可能又被切坏）。

所以名册注册应该放在**每次灌数据之前**，而不是服务启动时做一次。
如果将来接了实时写入，需要在写入路径上定期刷新名册。

这一点要写进文档，否则「孙柏林修好了、新来的人还是坏的」。

### 不做的事

- **不改 jieba 的词表**（那是上游，改了影响全局且不可控）
- **不加「姓 + 词」的组合规则**（穷举不完）
- **不试图识别名册外的三字人名**（超出本 spec，且风险高）

### 修法：名册绕过 jieba，不跟它对抗

用户给的判断是对的：**名册里出来的都是名字**。

三个权威来源（全是平台给的）：

| 来源 | 内容 |
|---|---|
| `list_dingtalk_contacts` | `uid → nick` |
| 群标题 | `孙柏林,王勇,任泽昂,王婕` |
| 消息 `sender` | 每条消息的发言人 |

机制（仿已有 `register_surnames` 的模式）：

```
register_roster(names) / reset_roster() / roster_names()
```

`extract_entities` 改成两段式：

```
1. 名册最长匹配 → 命中的收为 person，并把片段从文本**挖掉**
2. 剩余文本继续走 jieba（原逻辑不动）
```

**「挖掉」是关键**：不挖的话 jieba 会在剩余文本里再抽一次「柏林」，
同一个人变成两条记录。测试 `test_longest_match_wins` 钉住这一点。

### 名册必须随请求走，不能只注册在脚本里

第一次实现完发现一个坑：**`extract_entities` 跑在服务进程里**，
`seed_dingtalk.py` 注册名册没用 —— 那是另一个进程的模块级状态。

所以给 `IngestRequest` 加了 `roster` 字段：

```
IngestRequest(..., roster=["孙柏林", "刘阅", "王伟民"])
```

`/admin/ingest` 在切分前注册（`remember_event` 内部会调 `extract_entities`，
那时候名册必须在）。日志能看到：

```
ingest 注册名册 3 个（新增 3，总计 3）| job=dt:sub-sunbolin-...:s2
```

### 为什么不修 jieba

修 jieba 切分是**对抗一个通用分词器**，要穷举「姓 + 什么词」的组合，
永远有漏网的。

名册是**绕过分词**：平台已经告诉我们这些人叫什么，为什么还要用通用词典猜？

这和 026 的教训是同一个：**有确定性信息时，不要用概率模型去猜**
（那次是「用户配了同义词就不要让规则 1 抢」，这次是「平台给了名册就不要让 jieba 拆」）。

### 范围边界（明确不做）

- **不改 jieba 词表** —— 上游，改了影响全局且不可控
- **不加「姓 + 词」组合规则** —— 穷举不完
- **不识别名册外的三字人名** —— 超出本 spec，风险高

所以名册为空时，`孙柏林` 仍然变 `柏林`。测试
`test_empty_roster_keeps_original_behavior` 明确断言「没变化」而不是「正确」，
避免把已知缺陷伪装成修好了。

### 时效性注意

所以名册注册要放在**每次灌数据之前**，不是服务启动时做一次。
将来接实时写入，需要在写入路径上定期刷新。
