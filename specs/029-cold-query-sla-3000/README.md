# 029 冷查询目标放宽到 3s（SLA 护栏）

## Overview

028 实测出 `COLD_QUERY_P95_MS = 800` **处于临界**（三轮 P95 = 671 / 878 / 739ms）。
用户明确接受 3s，所以把目标值改成 3000。

### 这个改动改变了什么，没改变什么

**改变了**：告警阈值的语义。从「当前性能目标」变成「**防性能回归的硬护栏**」。
实测 P95 离 3000 还有 4 倍余量，所以它只在严重劣化时才响。

**没改变**：实际性能。代码一行没动，671–878ms 还是那个数。

### 800 去哪了

**留在 ADR 里当优化目标**，不加配置字段。理由：

- 它已经不是「会触发动作的阈值」，加字段就是一个永远不被读的配置
  （本项目对「写了不接」零容忍，`audit_config_usage.py` 会把它算成零引用）
- 它的价值在文档 —— 告诉后来人「曾经想做到 800，实测做不到，
  瓶颈已定位在 rerank 和 client 重建」

## Design

### D1 只改默认值，不动代码

`config.py`：`COLD_QUERY_P95_MS: int = 800` → `3000`

告警逻辑（`recall.py` 的 `finally`）不需要任何改动 —— 它读配置。

### D2 顺带修一处「已失效的对齐关系」

`VECTOR_TIMEOUT_MS` 的注释写着「与 `COLD_QUERY_P95_MS` 对齐」，
两者都是 800，所以当时确实对齐。

改成 3000 后**不对齐了**，这是必须处理的：
单通道超时 800ms 是合理的（一次 HTTP 不该等 3 秒），
它不该跟着 SLA 走。所以改的是**注释**，把对齐关系说清楚：

- `VECTOR_TIMEOUT_MS = 800` 对齐的是**优化目标** 800
- `COLD_QUERY_P95_MS = 3000` 是**SLA 护栏**

**不能**把 `VECTOR_TIMEOUT_MS` 也改成 3000 —— 那会让单个通道卡 3 秒，
三个并行通道最坏 3 秒，整次查询就贴着 SLA 了。超时值是「多久算异常」，
SLA 是「多久算不可接受」，两者本来就不该相等。

### D3 新增一条测试：默认配置下不产生噪声告警

现有测试都用显式覆写阈值（1 / 999999 / 0 / -1）验证「改配置 → 行为变」。
**没有一条**验证「**默认值本身**在当前性能下会不会天天报警」。

这条很重要：如果 3000 定得太低（比如 900），测试全绿但线上日志会被淹没。
所以要有一条用**默认配置** + 正常耗时的测试，断言不告警。

这条测试的耗时必须可控 —— 用 fake store 的固定延迟（几十 ms），
而不是真实查询，否则会 flaky。

### D4 ADR 用表格表达「两个数字，两种用途」

不能只把 800 改成 3000 就完事 —— 那样 028 记的实测表就失去参照。
要明确写：

| 数字 | 用途 | 超标会怎样 |
|---|---|---|
| 800 | 优化目标（028 实测未达成） | 什么都不发生 |
| 3000 | SLA 护栏 | 打 WARNING |

## 实现记录

### 改了什么

| 文件 | 改动 |
|---|---|
| `config.py` | `COLD_QUERY_P95_MS` 800 → **3000**，加注解说明它是 SLA 护栏 |
| `config.py` | `VECTOR_TIMEOUT_MS` 加注释：它对齐 800 的**优化目标**，不是 3000 的 SLA |
| `recall.py` | 「与 COLD_QUERY_P95_MS 对齐」的注释改为说明两者已不相等 |
| `.env.example` | 补上 `COLD_QUERY_P95_MS=3000`（原来**根本没有这一项**），修掉 `GRAPH_TIMEOUT_MS` 的过时注释 |
| `tests/test_recall_latency.py` | 加 2 条：默认值 3000 + 默认配置下不误报 |
| `ADR C.B12` | 改成「优化目标 800 / SLA 护栏 3000」双数字表格 |

全量 `1148 passed`（原 1146 + 2）。

### 改完实测：稳态 P95 838ms，但**启动首查 3018ms 撞线了**

```
COLD_QUERY_P95_MS : 3000 ms
P50 601.7  P95 837.8  P99 1093.1  max 1170.3   （25 次稳态样本）
P95 达成，余量 2162ms
```

稳态完全没问题 —— 余量 3.6 倍。但 warmup 那次：

```
冷查询耗时超目标 | 3017ms > 3000ms | 通道 {'vector': 8, 'bm25': 8, 'graph': 1356}
warmup 耗时 3018 ms
```

`graph` 通道首次 Neo4j 建连吃 1356ms，加上 jieba 加载、TEI 建连，
首查总计 3018ms。

**这意味着每次服务启动都会响一次告警**，而且只超 17ms —— 极端不稳定
（下次可能 2900 不响，下次 3100 又响）。

### 首查为什么会撞线：三个一次性开销

| 开销 | 量级 | 何时发生 |
|---|---|---|
| Neo4j 连接建立 | ~1356ms | 进程首查 |
| jieba 词典加载 | ~1s | 进程首查 |
| TEI / embedding 建连 | 数百 ms | 进程首查 |
| 稳态查询 | 454–1170ms | 之后每次 |

028 D5 已经写明「测的是暖启动后的冷 query，不含进程冷启动首查」，
当时没预料到的是：**首查的量级刚好落在新护栏的边上**。

### 没修，因为该修的地方不在 recall 里

`recall()` 是纯函数，**它不知道自己是第几次被调用**。想在里面豁免首查，
只能靠「进程启动时间戳 + 阈值」这种脆弱判断，会引入新的隐蔽状态。

正确的解法是**服务启动时预热一次**（HTTP 入口在 lifespan 里跑一次
dummy recall，MCP 入口同理），那样首查开销落在启动阶段，
第一个真实用户请求就是稳态速度。

**但这超出 029 范围**（029 只改阈值 + 文档），而且涉及：
- 预热要不要等它完成（阻塞启动 vs 后台）
- 预热失败怎么办（fail fast 还是继续）
- 两个入口（MCP stdio / HTTP）都要接

**记录待决**：要么接受「每次启动响一次警」，要么把预热做成单独一件事。

### 一个副产物：`.env.example` 缺项被发现了

改配置时才发现 `.env.example` **从来没有 `COLD_QUERY_P95_MS` 这一项**。
也就是说，这个参数在 028 之前既没被代码读、也没在示例配置里出现，
**只存在于 `config.py` 和 ADR 的表格里**。

这正是「写了不接」能藏这么久的原因 —— 示例配置是给人看的入口，
入口里没有的东西，没人会去问它为什么不起作用。已补上。

### 表里 `B12` 那一行的状态没动

`docs/ADR` 里 B12 的实现状态表仍写着 `P1 出口 / COLD_QUERY_P95_MS`。
它指的是「这个指标有没有被实现」，而不是「目标值是多少」——
028 接上了测量和告警，029 调了阈值，这一行的语义没变，不需要改。

## Notes

### 为什么这不是「把数字改大让它看起来达标」

区别在于**诚实性**：

- 坏做法：测出 878ms，把目标改成 3000，然后写「P95 已达标」。
  这是拿阈值掩盖事实。
- 这次做法：028 已经写明「800 处于临界、未达成、瓶颈在 rerank 和
  client 重建」。029 改的是**容忍上限**，并且 ADR 明确保留 800 作为
  未达成的优化目标。

**实测值没变，变的是「多慢算不可接受」这个产品判断。**
前者是事实，后者是决策 —— 不能混。

### 3s 这个数字从哪来

用户给的（2026-11-06）。不是测出来的，是**产品侧可接受上限**。

这类数字和 026 那个「向量阈值 0.92」性质不同：0.92 是**声称能从数据里
算出来**的（所以必须实测，实测发现不可分就要推翻），3s 是**人的偏好**
（没有「对不对」，只有「接受不接受」）。

分清这两类，才知道哪个该拿测量去质疑。

### 如果哪天 P95 真的接近 3000

那说明发生了四个数量级的性能退化，一定是结构性问题（不是负载波动）。
届时该做的是查根因，不是再调阈值 —— **阈值只能调两次**：
一次定产品可接受度，一次定回归护栏。第三次就是在骗自己。
