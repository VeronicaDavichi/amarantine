# 033 健康报告加震荡扫描

## Overview

032 让「规则震荡」显式化了（`UNKNOWN / rule="conflict"`），但震荡只在
**运行时**发生 —— `best_candidate` 里打一行 INFO 日志就没了。

**问题**：想知道「规则设计有没有问题」，得去翻日志，而日志可能没配、
可能被轮转、也没法回溯「这些数据本来会不会振荡」。

所以要在**离线**的健康报告里加一个震荡扫描：拿图里现有的实体名，
重放一遍投票，看有多少对震荡。

### 这不是「运行时震荡率」

两者不一样，必须说清楚：

| | 运行时震荡 | 离线震荡扫描 |
|---|---|---|
| 数据 | 真实发生的候选扫描 | 图里所有可能的名字对 |
| 意味 | 「系统实际遇到了多少」 | 「这批数据里潜藏多少矛盾」 |
| 依赖 | 日志配置、使用量 | 只依赖图，可随时重跑 |

离线扫描能回答「**规则在这批数据上自相矛盾吗**」，这是运行时日志答不了的
（没人触发的数据不会出现在日志里）。

## Design

### D1 扫哪些对：只扫「可能相关」的，不扫全量两两组合

全量两两是 O(n²)：1000 个实体 = 50 万对，大部分是彻底无关的
（`张三` vs `项目A` 永远 UNKNOWN，扫它没意义）。

只扫**有字面关系**的对，这些才是规则 1/2/3 的战场：

- 一个是另一个的前缀（`上海` / `上海市`）
- 编辑距离 ≤ 2（`张三` / `张四`、`豆包` / `豆包AI`）

**为什么编辑距离 2**：规则 1 只挡「长度差 1」，后缀/称呼规则最多加 4 个字
（`有限公司`）。距离 2 能覆盖单字后缀和单字称呼，多字后缀需要放宽 ——
所以实际用「前缀关系」为主，编辑距离作辅助。

### D2 分母要诚实：可扫描对太少时，别把 0 当作好消息

```
震荡扫描: 6 对可扫描（4 个实体名两两组合）
  震荡 0 对
  ⚠️ 可扫描对 < 50，这个数字没有统计意义
```

现在库里只有 4 个名字（项目A/项目B/张三/李四），两两 6 对，且互无关系
→ 震荡必然是 0。**这个 0 说明「数据太少」，不说明「规则好」**。

如果不加这句警告，将来有人看到「震荡 0」会以为规则层很健康。

### D3 列出具体震荡对，不只给数字

```
  震荡 2 对：
    张三 / 张三丰   同:[suffix] 不同:[single_char_prefix]
    上海 / 上海市   同:[suffix] 不同:[single_char_prefix]
```

数字告诉你「有没有问题」，明细告诉你「哪条规则和哪条打架」。
后者才是能动手改的东西。

### D4 复用 `match_entities`，不重写规则

扫描必须走**同一个** `match_entities` —— 否则扫出来的震荡和线上行为不一致，
报告就失去意义。

`match_entities` 返回 `rule="conflict"` 且 `reason` 里已经列了两边的规则名，
直接拿来用。

### D5 名字从哪来：图里的 Entity / Person

用 `(:Entity)` + `(:Person)` 的 `name` 属性，去重、排序。

**不用**卡片里的 `entity_names`：那是写入时的快照，可能和当前图不一致
（软删的卡、重建过的卡）。图才是「现在有哪些实体」。

### D6 上限保护

即使只扫「可能相关」的对，极端情况（大量相似名，比如 `项目A-1` 到
`项目A-999`）仍可能爆。加个上限：

- 最多扫 `MAX_PAIRS = 20000` 对
- 超了就截断并明确写「已截断，结果不完整」

不能默默截断 —— 那会让人以为扫完了。

## Notes

### 为什么不用日志统计

三个原因：

1. **日志可能没配**（`LOG_FILE` 是可选配置）
2. **会被轮转**，历史数据拿不到
3. **只反映被触发的**：没人查过的名字对永远不会出现在日志里，
   但它们潜藏的矛盾依然存在

离线扫描能随时重跑，是「这批数据 + 这套规则」的自洽性检查。

### 这个数字能回答什么，不能回答什么

**能**：规则之间有没有职责重叠到自相矛盾。

**不能**：判断哪个结论是对的。扫描只告诉你「这里两条规则吵架」，
哪边对需要看具体数据（`张三/张三丰` 如果真是笔名，同义词表能定音）。

### 与 `alias_reject` 的关系

`alias_reject` 表记录了「用户拒绝过的别名」。如果某个震荡对已经被用户
拒绝过，说明它的正确答案是「不同」—— 将来可以把这层信息喂给裁决，
减少震荡。本次不做（属于 `candidate_alias` 确认池那条线）。

先只做「能看见」。

## 实现记录

### 报告现在长这样

```
震荡扫描（4 个实体名）
  可扫描 0 对（全部两两组合 6 对）
  没有前缀关系的名字对
    → 规则 1/2/3 全要求「一个是另一个的前缀」，
      所以这个 namespace 结构上不存在震荡风险（不是数据好，是没有风险点）
```

有震荡时：

```
震荡扫描（5 个实体名）
  可扫描 4 对（全部两两组合 10 对）
  震荡 1 对（25.0%）
    明细（同 = 说相同的规则，不同 = 说不同的规则）：
      上海 / 上海市
        上海 / 上海市 规则矛盾 | 同: ['suffix'] 不同: ['single_char_prefix']
```

### 三次写错测试，每次都是「测试替身和真身不同构」

**第一次**：用「编辑距离 ≤ 2」筛候选对。

中文两字名的编辑距离几乎都 ≤ 2 —— `张三`/`李四` 是 2，`北京`/`南京` 是 1。
**等于没筛**，白扫一堆永远 UNKNOWN 的对。

改成只看**前缀关系**。理由：规则 1/2/3 全都要求「一个是另一个的前缀」，
那才是真正的战场。规则 4（同义词）不靠字面，扫不到 —— 但它优先级最高
不会震荡，漏掉没有影响。

**第二次**：monkeypatch `_graph_names` 时写 `sorted(names)`，没去重。

真实的 `_graph_names` 用 `set` 去重。于是 `["张三", "张三"]` 进去还是 2 个名字，
测出来的行为和线上不一致。**测试替身必须和真身同构**。

**第三次**：测「0 震荡」时用互不相关的名字。

前缀筛选会把它们全过滤掉，于是根本不进「震荡 N 对」那行 ——
测不到想测的东西。改用 `张三/张三丰`（有前缀关系、正常配置下只命中规则 1、
判 DIFFERENT 不矛盾）。

### meta-test 第一次也漏了，因为场景区分不开

注入「`rule == "conflict"` → `ruling == "unknown"`」后，造震荡的测试**照样过**。

原因：那个场景里 `上海/上海市` 既 `rule=conflict` 也 `ruling=unknown` ——
两种判定给同一个答案，区分不开。

加对照组 `阿里/阿里巴巴`：有前缀关系（会进扫描），但后缀表里没有「巴巴」
（规则 3 要求「差**一个**后缀」），规则 1 也不命中 → `UNKNOWN / rule=""`。

现在注入后它会多算一对震荡，断言就失败了。

**这证明「区分 conflict 和普通 UNKNOWN」是真需求，不是代码洁癖** ——
否则「规则不认识这俩」会被报成「规则打架」，震荡率虚高。

### 为什么不用日志统计震荡率

1. **日志可能没配**（`LOG_FILE` 是可选）
2. **会被轮转**，历史拿不到
3. **只反映被触发的**：没人查过的名字对永远不出现在日志里，
   但它们潜藏的矛盾依然存在

离线扫描能随时重跑，是「这批数据 + 这套规则」的自洽性检查。
两者回答不同的问题：

| | 运行时日志 | 离线扫描 |
|---|---|---|
| 数据 | 真实发生的候选扫描 | 图里所有可能的名字对 |
| 回答 | 「系统实际遇到多少」 | 「这批数据潜藏多少矛盾」 |

### 数字的地板

`MIN_MEANINGFUL_PAIRS = 50`。可扫描对少于此值时，0 震荡**必须**带警告：

```
⚠️ 可扫描对 < 50，这个 0 没有统计意义（数据太少，不代表规则没问题）
```

不加这句，将来有人看到「震荡 0」会以为规则层很健康 —— 而实际只是数据太少。
现在库里 4 个名字、0 对可扫，这个 0 连「扫过」都谈不上。

### 上限保护

`MAX_CONFLICT_PAIRS = 20000`。极端情况（`项目A-1` 到 `项目A-999` 这种）
仍可能爆。超了会明确写「已截断，结果不完整」—— **不能默默截断**，
那会让人以为扫完了。

### 这个数字能回答什么，不能回答什么

**能**：规则之间有没有职责重叠到自相矛盾。

**不能**：判断哪个结论是对的。扫描只告诉你「这里两条规则吵架」，
哪边对需要看具体数据 —— `张三/张三丰` 如果真是笔名，配个同义词表就能定音
（032 让同义词压过所有启发式）。
