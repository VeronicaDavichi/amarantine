# 032 规则震荡：投票 + 用户声明优先 + 矛盾交 LLM

## Overview

用户指出：**同一对名字在不同规则下来回震荡，此时应该依赖 LLM。**

实测后发现震荡有两种，**必须分开处理**，混在一起会修错一个。

### 震荡 A：用户声明 vs 启发式（这不是震荡，是优先级排错了）

```
配置 ENTITY_SYNONYMS="张三丰=张三"   # 用户明确说这俩是同一个
match_entities("张三", "张三丰")
→ different   rule='single_char_prefix'
```

**同义词表根本没机会执行** —— 规则 1（姓名结构）抢先返回了 DIFFERENT。

这是**真 bug**：用户显式声明的知识被启发式猜测覆盖了。
「张三丰」在真实场景里可能是笔名、艺名、曾用名，用户配同义词就是在纠正系统。

**交 LLM 是错的处理**：LLM 看到「张三 / 张三丰」也大概率说「不同」，
用户的声明等于白配。正确做法是**用户声明优先**。

### 震荡 B：两条启发式互相矛盾（这才是要交 LLM 的）

```
上海 / 上海市
  规则 1（姓名结构）：DIFFERENT   ← 「上」是姓，「上海」= 姓+单字名
  规则 3（后缀白名单）：SAME      ← 「市」是行政区后缀
```

**两条都是启发式，都没有用户声明背书**，谁也不能说谁更可信 ——
这就是该交给 LLM 的信号。

031 的修法是「规则 1 遇到已知后缀时弃权」，**把震荡消灭在源头**。
这在当前数据上有效，但代价是：每加一条规则就要再加一个「弃权例外」。
`_prefix_conflict_excluding_affix` 现在同时管称呼和后缀，将来还要管更多。

**本 spec 换一种结构**：不再靠「弃权」消除矛盾，而是**让矛盾显式化**。

## Design

### D1 所有规则都投票，不再「首个命中就返回」

```
旧：规则 1 命中 → 立刻 return
    规则 1 没命中 → 规则 2 命中 → return
    ...
    （顺序决定结论）

新：规则 1、2、3、4 全部跑完，收集所有结论
    → {SAME: [后缀, 同义词], DIFFERENT: [前缀]} 
    → 再按优先级裁决
```

**规则顺序不再影响结果**（除了同义词优先，见 D2）。这是根本解决 ——
将来加规则不需要再想「它该排在哪一条前面」。

### D2 裁决顺序：用户声明 > 启发式一致 > 矛盾交 LLM

```
1. 同义词表命中                      → SAME（用户声明，不管其他规则说什么）
2. 启发式结论唯一（只说同 / 只说不同） → 用该结论
3. 启发式结论矛盾                    → UNKNOWN（震荡，交 LLM）
4. 没有任何规则命中                   → UNKNOWN（交 LLM）
```

**为什么同义词压过一切**：它是**明确知识**，不是猜测。
规则 1 是「看字形猜这是人名」，同义词是「用户说这俩是一回事」。
明确知识被猜测覆盖，是设计错误。

**为什么启发式矛盾交 LLM 而不是定一个默认值**：
两条启发式都只是「大概率」，没有哪个更可信的依据。硬选一个就是
「按规则顺序碰运气」—— 031 那个 bug 正是这么来的。

### D3 `MatchResult` 要能表达「震荡」

`ruling=UNKNOWN` 不够 —— 调用方分不清「没规则命中」和「规则打架」。

```
MatchResult(
    ruling=UNKNOWN,
    rule="conflict",
    reason="后缀说同、姓名结构说不同",
)
```

这样审计日志能直接看出「这条是震荡交给 LLM 的」，而不是「规则不认识这俩」。

### D4 震荡要可观测

`alias_resolver` 已经在规则未命中时打日志才调 LLM。震荡多打一行：

```
规则震荡，交给 LLM | 上海 / 上海市 | 同:['suffix'] 不同:['prefix']
```

**为什么重要**：如果震荡率很高，说明规则设计有问题（或者数据分布和假设不符）。
没有这个数字，就不知道「交 LLM」是偶尔兜底还是天天兜底。

### D5 `best_candidate` 不用改

它只在 `result.is_same` 时返回候选。震荡 → UNKNOWN → 不返回 → 调用方调 LLM。
**兜底路径已经存在**，这次只改「什么时候产生 UNKNOWN」。

### D6 `ENTITY_RULE_ENABLED=false` 行为不变

关闭时只有规则 1 参与投票 → 不可能震荡 → 结论和现在一样。
但**同义词也应该关闭**吗？

**要**：同义词属于规则层的一部分。关闭规则层 = 不要任何规则判断。
用户显式声明的同义词也走规则层，一起关掉，行为退化为「全部交 LLM」。

这点要在测试里钉住，否则改完会出现「关掉规则层但同义词还生效」的半开状态。

## Notes

### 「交 LLM」不是免费的

震荡 → LLM 意味着：一次网络调用（约 200-2000ms）、一次 token 消耗、
以及 LLM 挂了就返回 None（放弃解析）。

所以**减少震荡本身有价值**。031 的「弃权」和本 spec 的「同义词优先」
都是减少震荡的手段，只是层次不同：

- 弃权：让某条规则**不表态**（它知道自己在这种情形下不可靠）
- 优先级：让更可信的规则**直接裁决**（不需要 LLM）

两者不冲突，可以并存。真正的震荡（两条都表态且矛盾）才交 LLM。

### 为什么不在 031 里一次做完

031 修的是**具体的地名 bug**，交付物是「上海/上海市 不再被拆开」。
本 spec 修的是**结构**：规则顺序不再决定结论，矛盾显式化。

混在一起做，如果结果不对，分不清是「地名修错了」还是「投票写错了」。
这也是 027/028/029 一路下来的同一条纪律：**一个 spec 只改一件事**。

### 震荡率是规则设计质量的指标

如果上线后震荡日志很多，说明：

- 规则之间职责重叠（多条规则都在管同一类情况）
- 或者数据分布和假设不符（比如大量外文名，姓名结构规则全失效）

这个数字应该在 `check_data_health.py` 里也有个位置（将来）。
本次先把「震荡可观测」这个能力交付，不做统计面板。

## 实现记录

### 震荡有两种，混在一起会修错一个

做之前先实测了 23 组对照，结果是 **0 组震荡** —— 因为 031 的「弃权」例外
已经把规则 1 和后缀/称呼规则的冲突消灭在源头了。

但顺着「震荡」这条线查下去，**挖到一个真 bug**：

```
配置 ENTITY_SYNONYMS="张三丰=张三"   # 用户明确说这俩是一个
match_entities("张三", "张三丰")
→ different   rule='single_char_prefix'
```

**同义词表根本没机会执行** —— 规则 1 抢先返回了。

所以震荡要分两类：

| 类型 | 例子 | 正确处置 |
|---|---|---|
| **用户声明 vs 启发式** | 配了 `张三丰=张三`，规则 1 说不同 | **听用户的**（不是交 LLM） |
| **启发式 vs 启发式** | `上海/上海市`：姓名结构说不同、后缀说是同 | **交 LLM** |

第一类如果交 LLM，LLM 看到「张三 / 张三丰」也大概率说「不同」，
用户的声明等于白配 —— 那配同义词表就毫无意义了。

### 改法：投票 + 同义词优先 + 震荡显式化

```
旧：规则 1 命中 → 立刻 return
    规则 1 没命中 → 规则 2 命中 → return
    （顺序决定结论）

新：四条规则全部跑完，收集票
    1. 同义词命中        → SAME（用户声明，压过一切）
    2. 只有一种结论      → 用它
    3. 两种结论都有      → UNKNOWN / rule="conflict"（震荡 → 交 LLM）
    4. 没有任何结论      → UNKNOWN（交 LLM）
```

**规则顺序不再影响结论** —— 这是投票结构存在的全部意义。
将来加规则不用再想「它该排在哪一条前面」。

### 震荡 → LLM 的兜底**本来就存在**

`alias_resolver` 的流程是：

```
best_candidate() 命中 SAME → 用规则结果（source="rule"）
没命中（None）        → 调 LLM
```

所以只要震荡返回 UNKNOWN（不满足 `is_same`），`best_candidate` 就跳过它，
调用方自动走 LLM。**调用方一行没改。**

震荡日志打在 `best_candidate` 里，因为 `match_entities` 是纯判定函数，
它不知道自己是「在一次候选扫描中被调用」还是「单独被调用」。

### 031 的「弃权」和 032 的「投票」并存，不冲突

- **弃权**：这条规则知道自己在这种情形下不可靠，**不表态**
- **投票**：多条规则都表态时，才需要裁决

保留弃权能**减少不必要的 LLM 调用**：「上海/上海市」明显是同一地，
没必要为了裁决去问一次模型。所以 032 没有把 031 的例外删掉。

两者分工：弃权管「什么时候闭嘴」，投票管「吵起来了怎么办」。

### 又一个我写错的期望值

spec 里 D6 我写「`ENTITY_RULE_ENABLED=false` + 同义词 → UNKNOWN」。

实测是 **DIFFERENT** —— 因为规则 1 永远生效（spec 020 的既有功能），
它仍会判「张三/张三丰」不同。同义词确实被一起关掉了（没偷偷生效），
但剩下那条规则还是会给结论。

**这是第二次同类错误**（031 里我把 `项目A/项目A组` 期望成 DIFFERENT，
实际是 UNKNOWN）。两次都是「我以为关闭某个东西会让结果变成 UNKNOWN，
实际上还有别的规则在表态」。

已改正 spec，并在测试 docstring 里写明期望是 DIFFERENT 及原因。

### 验证

| 场景 | 结果 |
|---|---|
| `张三丰=张三` + `张三/张三丰` | ✅ SAME / `synonym`（修好了） |
| 无同义词 + `张三/张三丰` | ✅ DIFFERENT / `single_char_prefix`（031 行为不变） |
| `上海/上海市` | ✅ SAME / `suffix`（弃权仍生效，无震荡） |
| 人为造震荡（移除弃权 + 「丰」进后缀表） | ✅ UNKNOWN / `conflict`，reason 列出两边规则 |
| 规则层关闭 + 同义词 | ✅ DIFFERENT（同义词没偷偷生效） |
| 震荡候选 | ✅ 打 INFO 日志，且跳过它继续试其他候选 |

meta-test：`2/2` 注入被抓住 —— 去掉同义词优先会失败、震荡时改回
「取第一票」也会失败。第 2 条尤其重要：如果注入后震荡测试还过，
说明它只是碰巧命中了 UNKNOWN，没在测「矛盾被显式化」。

### 震荡率是规则设计质量的指标

如果上线后震荡日志很多，说明规则之间职责重叠，或数据分布和假设不符
（比如大量外文名，姓名结构规则全失效）。

`best_candidate` 里打 INFO 日志就是为了能回答这个问题 ——
没有这个数字，就不知道「交 LLM」是偶尔兜底还是天天兜底。

统计面板没做（本次只交付「可观测」这个能力）。
