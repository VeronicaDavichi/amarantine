# 每张卡挂了整个 30 条窗口，而不是它自己的那几条原文

## Overview

**主人澄清的原始设计**：

> 30 条是一个滑动窗口，在窗口内归类事项，每个短时间内发生的事情归在一起，
> 这些原文聚合在一起是一张卡片。

也就是：窗口 = 上下文，窗口内多个「事项」各成一张卡，
**每张卡的 `raw_quote_ids` 应该只有这个事项的那几条原文**。

**实际实现是 `raw_quote_ids=list(quote_ids)`** —— 整批 30 条挂到每张卡。

实测（2026-11-27，namespace `qq-505456846`）：

| 项 | 实测 |
|---|---|
| 每卡原文条数 | P50 = P90 = max = **30** |
| 一窗切出多少卡 | 4383 卡 / (9112 条 ÷ 30) ≈ **14 张/窗** |
| 每卡本该挂几条 | **约 2 条**（30 ÷ 14） |
| 实际总挂载 | 129156 条关联（原文只有 9112 条，冗余 14 倍） |

## 这个 bug 解释了之前所有「想不通」的现象

诊断召回质量时一路挖，根因都指向这里：

| 现象 | 因为整批挂载 |
|---|---|
| 90% 的原话与卡片摘要**零内容交集** | 摘要只写一个话题，窗口里却有 14 个话题 |
| 卡级向量稀释（纯向量 hit@5 0.400） | 30 条混成一个向量 |
| 「每原文一向量」也失败（0.267） | 同卡其余原文根本不相关 |
| `RAW_TEXT_INDEX_MAX_CHARS` 要截断 | 一卡 900–1200 字 |
| 摘要 P50 只有 17 字 | 要概括 14 个话题，只能写「群友在聊天」 |

**spec 051/052 都是在修补它造成的后果。**

## Design

### 修复：按 `source_indices` 映射

`split_with_sources` 产出的事件本来就带 `source_indices`（1-based，指向本批 turns），
`_event_time` 已经在用它算时间 —— 只是没用来映射 `quote_ids`。

```python
def quotes_for_event(event, quote_ids, turns_count) -> list[str]:
    """这张卡该挂哪些原文（按 source_indices，不是整批）。"""
    # 越界跳过、去重保序
    # 没有 source_indices / 全部越界 → 退回整批（保住溯源，宁可多挂）
```

`quote_ids` 与 `usable` turns 索引对齐（入口按同一顺序生成），所以映射是安全的。

### 兜底：没有 source_indices 时退回整批

`_event_time` 的注释已经写明「模型没给 source_indices 时用 4-gram 兜底」，
说明确实存在没给的情况。这时**必须退回整批** —— 原文是事实层，
卡挂丢了就查不回去。宁可多挂。

## 存量怎么办（结论：只能重灌）

`source_indices` 当时没有存下来，所以无法直接重建。试过用摘要 4-gram 反查：

| 指标 | 结果 |
|---|---|
| 匹配成功 | 1261 / 4382（29%） |
| 回退整批 | 3121（71%） |
| 平均每卡 | 29.5 → 22.4 条 |

**不可行**：摘要改写了措辞，字面重合度太低；命中的还常是 QQ 卡片 JSON。

所以存量只有一条路：**重灌语料**（重新切分，`source_indices` 这次会被用上）。

## Notes

### 为什么这个 bug 能活这么久

因为**它不破坏任何功能**：卡能建、能召回、能查原文。只是每一层都「差一点」，
而「差一点」分散在摘要质量、向量稀释、BM25 精度几个地方，
看起来像是**算法问题**，不像**数据接错**。

我是顺着「90% 原话与摘要零交集」一路往回挖才发现的。
最初还以为是切分器太粗 —— 实际上切分器没问题（它给了 `source_indices`），
是**下游没用它**。

### 一个可以推广的排查方法

当「多个指标同时不理想」时，先怀疑**上游数据接错**，而不是挨个调下游算法。
本例中三路（摘要 / 向量 / BM25）同时表现差，本该立刻怀疑它们的共同输入。
